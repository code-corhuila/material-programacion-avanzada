Introducción

Esta es la Guía 2 de 2. En la guía anterior construiste el backend (NestJS + Prisma + PostgreSQL). Ahora vas a construir desde cero el frontend que se comunicará con esa API REST.

Requisito previo

Debes haber completado la Guía 1 — Backend + Base de Datos antes de comenzar. El backend debe estar corriendo en http://localhost:3001/api/v1 y la base de datos PostgreSQL activa en Docker.

¿Qué vas a construir?

El frontend del Sistema de Gestión Académica: una aplicación Next.js con App Router, TypeScript, Tailwind CSS v4, un cliente HTTP centralizado, y una capa de 8 servicios que se conectan a la API del backend. Todo preparado para Docker.

Arquitectura del Sistema

En esta guía nos enfocamos en la capa Frontend (Next.js), el cliente HTTP y los servicios que consumen la API REST:

▲

Next.js 16 — App Router

Framework React con renderizado del servidor, rutas basadas en carpetas y soporte nativo para TypeScript. Corre en el puerto 3000.

React 19

Librería de UI basada en componentes. Next.js se encarga de la configuración, tú solo escribes componentes .tsx.

Tailwind CSS v4

Framework CSS de utilidades. En v4 se configura como plugin de PostCSS — sin archivo tailwind.config separado.

TS

TypeScript 5

Tipado estático para JavaScript. Interfaces, genéricos y DTOs tipados para la comunicación con la API.

Paso 2 — Configurar next.config.ts

2

Agregar output: "standalone" para Docker

Genera un build optimizado con todo lo necesario para ejecutar sin node_modules

Abre frontend/next.config.ts y reemplaza todo su contenido con:

frontend/next.config.ts import type { NextConfig } from "next"; const nextConfig: NextConfig = { output: "standalone", // Necesario para Docker — genera un build auto-contenido }; export default nextConfig;

¿Qué hace output: "standalone"?

Cuando ejecutas npm run build, Next.js genera una carpeta .next/standalone/ que incluye un server.js y solo las dependencias necesarias. Esto permite crear imágenes Docker mucho más livianas sin necesidad de copiar todo node_modules/.

Paso 3 — Crear la Variable de Entorno

3

Crear .env.local con la URL del backend

Configurar la dirección donde el frontend se conectará a la API

Crea el archivo frontend/.env.local con este contenido:

frontend/.env.local NEXT_PUBLIC_API_URL=http://localhost:3001/api/v1

¿Por qué NEXT_PUBLIC_?

En Next.js, solo las variables que empiezan con NEXT_PUBLIC_ son accesibles desde el navegador (código del cliente). Las variables sin ese prefijo solo están disponibles en el servidor (API routes, Server Components). Como nuestro cliente HTTP se ejecuta en el navegador, necesita el prefijo.

Tip: El archivo .env.local ya está incluido en el .gitignore que generó create-next-app. Nunca se sube a Git.

Paso 4 — Crear el Archivo de Tipos Globales

4

Crear src/types/global.d.ts

Archivo de declaraciones para que TypeScript reconozca las variables de entorno de Node

Crea la carpeta frontend/src/types/ y dentro crea el archivo global.d.ts:

frontend/src/types/global.d.ts /// <reference types="node" />

¿Para qué sirve?

Esta línea le dice a TypeScript que incluya los tipos de Node.js (como process.env). Sin ella, TypeScript puede lanzar el error Cannot find name 'process' cuando el cliente HTTP intenta leer process.env.NEXT_PUBLIC_API_URL.

Paso 5 — Crear el Cliente HTTP Centralizado

5

Crear src/lib/api.ts — Cliente HTTP con Fetch

Un módulo que encapsula todas las peticiones HTTP a la API del backend

Crea la carpeta frontend/src/lib/ y dentro crea api.ts:

frontend/src/lib/api.ts // ============================================================ // lib/api.ts — Cliente HTTP centralizado // Base URL configurable desde variable de entorno // ============================================================ const BASE_URL = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:3001/api/v1"; type HttpMethod = "GET" | "POST" | "PUT" | "PATCH" | "DELETE"; interface ApiResponse<T> { statusCode: number; message: string; data: T; } async function request<T>( method: HttpMethod, path: string, body?: unknown ): Promise<T> { const options: RequestInit = { method, headers: { "Content-Type": "application/json", }, }; if (body !== undefined) { options.body = JSON.stringify(body); } const res = await fetch(`${BASE_URL}${path}`, options); if (!res.ok) { const error = await res.json().catch(() => ({})); const messages: string[] = error.message ?? ["Error desconocido"]; throw new ApiError(res.status, messages); } const json: ApiResponse<T> = await res.json(); return json.data; } export class ApiError extends Error { constructor( public readonly status: number, public readonly messages: string[] ) { super(messages.join(", ")); this.name = "ApiError"; } } export const api = { get: <T>(path: string) => request<T>("GET", path), post: <T>(path: string, body: unknown) => request<T>("POST", path, body), put: <T>(path: string, body: unknown) => request<T>("PUT", path, body), patch: <T>(path: string, body: unknown) => request<T>("PATCH", path, body), delete: <T>(path: string) => request<T>("DELETE", path), };

¿Cómo funciona este cliente?

  • BASE_URL — Lee la URL de la variable de entorno NEXT_PUBLIC_API_URL. Si no existe, usa localhost:3001 como fallback.
  • request<T> — Función genérica que acepta cualquier tipo. TypeScript infiere el tipo de retorno según lo que declares al llamarla.
  • ApiResponse<T> — Coincide con el formato que devuelve el backend: { statusCode, message, data }. La función extrae solo data.
  • ApiError — Clase de error personalizada con el status HTTP y los mensajes. Útil para mostrar errores en la UI.
  • api — Objeto con 5 métodos: get, post, put, patch, delete. Cada servicio los usará.
¿Por qué no usar Axios? Next.js mejora la función nativa fetch() con caché y revalidación automática. Usar fetch directamente aprovecha esas optimizaciones.

Paso 6 — Crear los 8 Servicios de Entidades

Cada servicio encapsula las llamadas HTTP de una entidad específica. Crea la carpeta frontend/src/services/ y dentro crea los siguientes 9 archivos (8 servicios + 1 barrel export):

6A

programas.service.ts — Programas Académicos

CRUD completo para la entidad ProgramaAcademico

frontend/src/services/programas.service.ts import { api } from "@/lib/api"; export interface ProgramaAcademico { id: number; nombre: string; codigo: string; facultad: string; duracionSemestres: number; } export type CreateProgramaDto = Omit<ProgramaAcademico, "id">; export type UpdateProgramaDto = Partial<CreateProgramaDto>; export const programasService = { findAll: () => api.get<ProgramaAcademico[]>("/programa-academico"), findOne: (id: number) => api.get<ProgramaAcademico>(`/programa-academico/${id}`), create: (data: CreateProgramaDto) => api.post<ProgramaAcademico>("/programa-academico", data), update: (id: number, data: UpdateProgramaDto) => api.put<ProgramaAcademico>(`/programa-academico/${id}`, data), remove: (id: number) => api.delete<void>(`/programa-academico/${id}`), };

Patrón de cada servicio

  • interface — Describe la forma del objeto que devuelve la API (coincide con el modelo Prisma)
  • CreateDto — Omit<Entidad, "id"> elimina el campo id (lo genera la BD automáticamente)
  • UpdateDto — Partial<CreateDto> hace todos los campos opcionales (actualizaciones parciales)
  • service — Objeto con los métodos CRUD que llaman al cliente HTTP

index.ts — Barrel Export

Re-exporta todos los servicios desde un solo punto de entrada

Crea frontend/src/services/index.ts:

frontend/src/services/index.ts // services/index.ts — Re-exports de todos los servicios export * from "./programas.service"; export * from "./estudiantes.service"; export * from "./docentes.service"; export * from "./asignaturas.service"; export * from "./periodos.service"; export * from "./asignaciones.service"; export * from "./matriculas.service"; export * from "./calificaciones.service";

¿Qué es un barrel export?

En vez de importar cada servicio desde su archivo individual, el barrel export permite importar todo desde un solo punto:

Ejemplo de uso // ❌ Sin barrel — importaciones largas import { programasService } from "@/services/programas.service"; import { estudiantesService } from "@/services/estudiantes.service"; // ✅ Con barrel — todo desde un solo import import { programasService, estudiantesService } from "@/services";

Paso 7 — Personalizar el Layout

7

Ajustar src/app/layout.tsx

Configurar fuentes, clases globales y metadata del proyecto

Abre frontend/src/app/layout.tsx y reemplaza todo su contenido con:

frontend/src/app/layout.tsx import type { Metadata } from "next"; import { Geist, Geist_Mono } from "next/font/google"; import "./globals.css"; const geistSans = Geist({ variable: "--font-geist-sans", subsets: ["latin"], }); const geistMono = Geist_Mono({ variable: "--font-geist-mono", subsets: ["latin"], }); export const metadata: Metadata = { title: "Create Next App", description: "Generated by create next app", }; export default function RootLayout({ children, }: Readonly<{ children: React.ReactNode; }>) { return ( <html lang="en" className={`${geistSans.variable} ${geistMono.variable} h-full antialiased`} > <body className="min-h-full flex flex-col">{children}</body> </html> ); }

¿Qué hace este layout?

  • Geist y Geist_Mono — Fuentes modernas de Vercel, cargadas con next/font/google para optimización automática
  • h-full antialiased — Clases de Tailwind para que el HTML ocupe toda la altura y suavice las fuentes
  • min-h-full flex flex-col — El body ocupa al menos toda la pantalla y usa flexbox vertical
  • metadata — Next.js usa esto para generar las etiquetas <title> y <meta description>
Tip: No toques page.tsx por ahora — la página por defecto de Next.js sirve para verificar que todo funciona. Más adelante la reemplazarás con tu propia UI.

Paso 9 — Crear el Dockerfile del Frontend

9

Crear el Dockerfile multi-stage para producción

Imagen optimizada que usa el build standalone de Next.js

Crea el archivo frontend/Dockerfile:

frontend/Dockerfile # ============================================================ # Dockerfile — Frontend Next.js # ============================================================ # --- Build stage --- FROM node:22-alpine AS builder WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build # --- Production stage --- FROM node:22-alpine AS production WORKDIR /app ENV NODE_ENV=production COPY --from=builder /app/.next/standalone ./ COPY --from=builder /app/.next/static ./.next/static COPY --from=builder /app/public ./public EXPOSE 3000 CMD ["node", "server.js"]

¿Cómo funciona?

  • Stage 1 (builder) — Instala dependencias, ejecuta npm run build. Gracias a output: "standalone", genera .next/standalone/ con server.js incluido
  • Stage 2 (production) — Solo copia: standalone/ (servidor + dependencias mínimas), .next/static/ (CSS/JS estáticos) y public/ (imágenes, SVGs). Sin node_modules/ completo
  • node server.js — El server.js generado por Next.js standalone levanta el servidor en el puerto 3000

Importante: output: "standalone" es obligatorio

Si no tienes output: "standalone" en next.config.ts (Paso 2), el build no genera .next/standalone/ y el Dockerfile fallará con "COPY failed: file not found".

Errores Comunes y Soluciones

Errores que puedes encontrar durante la creación del frontend y cómo resolverlos:

Error Causa Solución
Cannot find name 'process' Falta el archivo global.d.ts Crear src/types/global.d.ts con /// <reference types="node" />
Module not found: Can't resolve '@/lib/api' El archivo api.ts no existe o el alias @/* no está configurado Verificar que src/lib/api.ts existe y que tsconfig.json tiene "paths": { "@/*": ["./src/*"] }
La variable NEXT_PUBLIC_API_URL es undefined Falta el prefijo NEXT_PUBLIC_ o el archivo .env.local no existe Verificar que el archivo se llama .env.local (no .env) y que la variable empieza con NEXT_PUBLIC_. Reiniciar npm run dev después de crear/modificar el archivo
CORS: Access-Control-Allow-Origin El backend no tiene CORS habilitado Verificar que main.ts del backend tiene app.enableCors() (esto ya se hizo en la Guía 1)
EADDRINUSE :::3000 Puerto 3000 ocupado por otro proceso Cerrar el proceso anterior o ejecutar: npx next dev -p 3001 (aunque mejor cerrar lo que ocupa el puerto)
COPY failed: file not found in build context (Docker) El build standalone no se generó Verificar que next.config.ts tiene output: "standalone" y ejecutar npm run build antes del build de Docker
fetch failed o Network Error El backend no está corriendo Verificar con Invoke-WebRequest http://localhost:3001/api/v1. Si falla, ir a backend/ y ejecutar npm run start:dev
Cambios en .env.local no se reflejan Next.js cachea las variables de entorno al iniciar Detener el servidor (Ctrl+C) y reiniciar: npm run dev
